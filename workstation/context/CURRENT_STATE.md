## Working on current `main`

- Hermes Workstation is integrated into this downstream fork and the Desktop application can expose a dedicated `Browser` route.
- The internal browser runtime uses Electron Chromium through `WebContentsView` with a persistent Electron session/partition.
- Manual Browser navigation, tab creation/activation/close, back/forward/reload, pause/resume, focus, and human/agent control ownership are implemented.
- The Workstation controller is localhost-bound and token-authenticated.
- `browser_*` routing attempts the Workstation controller before fallback and has tests for bound fail-closed behavior and routing-disabled/internal-only behavior.
- **Desktop Browser schema capability is session-scoped.** A Desktop session preserves the Workstation-routed browser schemas even when controller reachability is temporarily false during startup. Reachability/recovery remains an execution-time concern; it no longer erases a valid Desktop surface from the model schema.
- The schema capability path is derived from Gateway session context (`source`/`platform`), not from `HERMES_DESKTOP` or another process-global Desktop identity flag.
- The tool-definition cache fingerprints the session-surface capability, preventing a Desktop schema result from leaking into TUI/CLI sessions that request the same toolsets.
- The browser profile preserves Chromium-managed site state such as cookies/localStorage/IndexedDB independently of renderer UI state.
- Existing Workstation lock, license, routing, and core-integration contract tests run in `Workstation CI`.
- The downstream `main` is the canonical source of Workstation core integration. Normal `workstation/install.cmd` validates committed integration in read-only mode, installs isolated dependencies, prepares runtime state outside the checkout, and asserts that it did not change Git-visible checkout state.
- Electron WebContents lifecycle compatibility (`webContents.close()`) is committed in the runtime itself rather than generated by install/CI.

## Implemented in the Implementation 4 candidate

The candidate formalizes BrowserTask without replacing the existing Chromium ownership primitives:

- `BrowserTask` is a first-class logical lifecycle object with `create`, `show`, `hide`, `park`, and explicit `destroy` semantics.
- `taskTabs` plus `BrowserEntry.ownerTaskId` remain the authoritative in-process task → live-page binding; BrowserTask metadata wraps that relationship instead of owning a second `WebContentsView` map.
- Repeated creation for the same `taskId` is idempotent at the Chromium tab primitive and does not allocate a second live task page.
- Within one Electron process, `hide` and `park` preserve the task page; a later `show` re-exposes the same `WebContents` with its current URL rather than navigating a replacement page.
- Showing a different BrowserTask parks the previously visible BrowserTask semantically as well as physically.
- `destroyTask` is distinct from hide/park and explicitly removes the logical task and closes its owned page.
- Missing/crashed task pages may be recovered with exactly one replacement page while the logical task remains, recording `recoveryState: recreated`.
- BrowserTask safe metadata is versioned and atomically persisted under the Workstation runtime directory. Invalid records are ignored and duplicate task ids are deduplicated by the most recent valid metadata.
- Desktop process restart restores logical BrowserTask metadata as `parked` / `recoveryState: restored` before recreating any page. A page is created lazily only when the restored task is used again.
- Restart recovery intentionally does **not** claim that a process-local `WebContentsView`, JavaScript heap, or renderer object survives application restart.
- Pure lifecycle tests and a `WorkstationBrowserRuntime` adapter test exercise these invariants without Browserless or network access.
- The Windows workflow contains a separately visible BrowserTask-focused test step in addition to the broad Desktop UI/platform suites, so baseline failures cannot hide the scoped lifecycle result.

## Partially implemented

- BrowserTask logical metadata now has candidate persistence, but the complete BrowserSessionState is not implemented: ordinary user-created tab ordering, active generic tab, richer URL/title restoration, and all controller/session/run/Kanban linkage are not yet a complete durable model.
- The `Browser` route is still a conventional browser tab strip and address bar. It is not yet the BrowserTask Hub described by the target architecture.
- Preview and Workstation Browser remain separate lanes/runtimes. They can represent different pages instead of two views of one BrowserTask.
- The browser host already observes geometry with `ResizeObserver`/`getBoundingClientRect`, but host ownership is not unified with Preview/Chat composition.
- BrowserTask metadata includes host/session/control linkage fields, but Implementation 4 does not yet claim full integration of those fields with Hermes SessionDB, Kanban, run orchestration, or controller recovery.

## Not implemented yet

- A contextual Chat Browser View backed by the same live page as the Browser Hub.
- Browser Hub task groupings such as active, waiting-for-human, background, and recent.
- A complete single-host ownership contract for moving one live `WebContentsView` between Chat and Browser Hub.
- Full versioned BrowserSessionState persistence/restoration for all logical tabs, active tab, ordering, and BrowserTask linkage.
- Preview compatibility adapters that reuse the Workstation BrowserRuntime instead of creating an independent browsing lane.
- The complete Desktop E2E proving Chat → BrowserTask → Chat view/Hub → hide/reopen → resize → restart/restore.
- The real Windows Desktop smoke required to accept Implementation 4 as stable. Automated Electron mocks/typechecks do not substitute for this native-view validation.

## Manual validation already observed

During the original bootstrap validation cycle, the Desktop app and the dedicated `Browser` route were opened successfully and manual navigation worked. The same cycle exposed the semantic integration gaps recorded below: Preview and Browser could show different pages and logical tabs did not survive application restart. The earlier symptom where the model reported no main Browser tool is now protected by the session-capability regression tests introduced in Implementation 3.

No manual observation from the bootstrap cycle proves the new Implementation 4 lifecycle candidate. Before PR #9 can be promoted, a real Windows Desktop build from the candidate must execute the narrower lifecycle smoke defined in `TESTING.md`: create/navigate a task page, hide or park it, re-expose it without a replacement navigation, explicitly destroy it, then restart and verify logical BrowserTask restoration/recovery behavior. Later Chat/Hub/Preview host-transfer steps remain future implementations.

Manual validation is evidence, not a substitute for automated regression coverage, and automated mocks are not a substitute for the required native smoke.
